## B1 — hover/active 伪类刷新「时好时坏」

### 根因（已读 stage.rs:456/459 核实）

`tick_and_render` 里 `compute_world_transforms`（**line 456**）在 `rematch_pseudo_classes`（**line 459**）**之前**跑。

- `:active{transform:scale(0.95)}` 经 rematch 写进 `node.style.transform`（`style/dynamic.rs:225`），但 compute 本帧已用**旧** transform 算完 world_matrix → `build_render_nodes` 读到无 scale 的 world（`render/mod.rs:140-144`）→ hash 不变 → emit `Unchanged` → scale 本帧不可见。
- 注释 stage.rs:458 自承「视觉变本帧 render 吃到」——对 bg_color 对，**对 transform 错**。

### 关键纠偏（已读 dirty.rs:14/39 核实）

dirty hash 字段集**是完整的**：`world_matrix`（含 scale 的 a/d 分量，dirty.rs:14）、`colors[0]`（hover 变色，dirty.rs:39）都在 hash 输入里。原 bug 清单主假设「dirty hash 没覆盖伪类样式变化」**不成立**——这是**时序 bug**，不是 hash 设计 bug。

### 「时好时坏」精确机理（帧序列）

- 帧 N（Down）：process 设 `active=true`(stage.rs:444) → compute(456) 读旧 `style.transform=identity` → world 无 scale → rematch(459) 设 `style.transform=scale` → build(464) 读 world（旧）→ hash 不变 → **Unchanged → scale 不可见**。
- 帧 N+1：compute 读上帧 rematch 设的 scale → world 含 scale → 若仍 hold，build 读 world（含 scale）→ hash 变 → emit → **可见**；若已 Up，rematch 回 identity 但 world 仍含上帧 scale → emit scale 1 帧 → 帧 N+2 才回正。
- 快击（Down+Up ≤1 帧）：scale 窗口完全错过，或 Up 后闪 1 帧 = **「点击偶有反馈」**。

### 关于 hover 变色（重要纠偏）

core 层 hover 变色逻辑链**完全正确**：rematch(459)→build(464) 读新 bg_color→`colors[0]`→hash 变→非 Unchanged（`build_changed_frame_re_emits` 测试锁定）。

**若 Unity 里 hover 变色也不刷新**，根因在 **C# 侧**（最可能 merge 镜像残留），不在 core。

**诊断一刀切**：dump hover 帧 `frame.nodes`，看 btn payload：
- 是 `Mesh{colors=蓝}` → core 对、问题在 C#（查 MirrorPool 对 merge 解除/节点消失时的镜像清理，render/merge.rs + batch.rs）。
- 是 `Unchanged` → core 错（但代码读下来不会发生）。

### 修复（高置信、零性能、低风险）

把 `compute_world_transforms` 从 stage.rs:456 移到 rematch（line 459）**之后**、build（line 464）之前：

```
// 改后顺序：
// ... process / scroll / keys (444-454)
rematch_pseudo_classes(scene);                                   // 先改 style（含 transform）
crate::scene::transform::compute_world_transforms(scene);        // 再算 world → 吃到新 transform
let (frame, new_hashes) = build_render_nodes(...);
```

**副作用已核查（低风险）**：
- hit_test（用上帧 world_transforms，1 帧延迟语义，stage.rs:414-419）：compute 仍在 process 之后，hit_test 仍用上帧 world → **不受影响**。
- scroll_pos 同帧进 world（drag 零延迟）：compute 仍在 process/scroll 之后，rematch 不动 scroll_pos → **不受影响**。原注释「compute 在 process/scroll 后」的本意（scroll 零延迟）只依赖「compute 在 process/scroll 之后」，移到 rematch 后仍满足。

**不要做（YAGNI）**：不要给 Node 加 `transform_dirty` flag——根因是 compute 时机，不是缺 dirty 机制；build_render_nodes 本就重算 hash 不依赖 dirty flag。不要在 rematch 内单独重跑 compute（双跑浪费）。

### 置信度 + 待验

- active scale 根因：**高**（多处 file:line 证据）。
- hover 变色归因为 C# merge 侧：**中**（未现场证实，需 dump）。
- **待验**：active 按下状态（非松开后）dump world_matrix 的 a/d 分量是否 0.95——若仍 1.0，直接坐实时序 bug。

## B2 — 图片显示为白块

### 根因（已读 LoomShowcaseAtlas.spriteatlas 核实）

atlas **从未 pack**：
- `:36` packables 是 `type:3` **文件夹**（整个 `icons/` 目录拖进 packables）；
- `:40` `packedSpriteRenderDataKeys: []`、`:42` `m_PackedSprites: []`、`:43` `m_PackedSpriteNamesToIndex: []` **三空**；
- `:38` `isAtlasV2: 0`（V1 atlas）。

极可能 Unity 6 对 **folder packable** 支持失效（V2 已移除 folder 支持，V1 在 6.5 下行为可能不一致），或 Sprite Packer 模式禁用 / Include in Build 未勾 / 从没点 Pack Preview → folder 静默打成空。

### 关键纠偏（已读 SpriteResolver.cs:80 + MirrorPool.cs:139 核实）

映射逻辑**其实是对的**：
- MirrorPool.cs:139 `sprites.GetSprite(path)` 传全 path（`"icons/home.png"`）→
- SpriteResolver.cs:80 `Path.GetFileNameWithoutExtension(path)` → `"home"` →
- `atlas.GetSprite("home")`。

而 home.png 是 `spriteMode:1` Single（`home.png.meta:46`），sprite 默认 name 就是 `"home"`。**key 正确**，但 atlas 空 → 任何 key 都查不到 → null。

原 bug 清单建议的「打包器锁定 path→sprite_name 进 manifest」**修不了这个**（atlas 空时无 key 可查）。path↔name 映射缺失是真实架构异味（中长期脆弱性来源），但**不是本次 null 的即时病因**。

### Unity SpriteAtlas 命名契约（GetSprite key 规则）

`U2D.SpriteAtlas.GetSprite(string name)`：clone 第一个 **name 匹配的被 pack 进来的 Sprite**。
- key = 被 pack 进来的 Sprite 子资产自身的 `name`（不是文件路径、不带扩展名、不带目录前缀）。
- spriteMode:1 Single → name 默认 = 资产名 = `"home"`。
- 大小写敏感；重名只返第一个。
- 返回 clone，`.texture` 指向 atlas 打包纹理。

### 修复

**前置诊断（必做、零代码）**：`SpriteResolver.cs:89` 的 `[IMG]` log 加 `atlas.spriteCount`，并临时枚举 `atlas.GetSpriteAtlas().GetSprites()` 打印实际名字。**9 成把握输出 `spriteCount=0`**，坐实「atlas 没 pack」。

**若 spriteCount==0（最可能）—— Unity 资产设置修，不用改代码**：
1. atlas packables 从 **folder 改成逐个 Sprite** 拖进去（避开 Unity 6 folder packable 失效）；
2. Project Settings → Editor → Sprite Packer 设 **Always Enabled**；
3. atlas inspector 勾 **Include in Build**；
4. 点 **Pack Preview**。
任一组合即可修好。

**可选代码兜底（YAGNI，非必须）**：包管理器面板（复用 `Editor/PkgManifestReader.cs`）加 authoring 期校验——对每个 manifest path 的 stem，注册的 atlas 必须 `spriteCount>0` 且 `GetSprite(stem)` 命中，否则红字报「atlas 未 pack / 缺 sprite」。把 B2 这类问题永久挡在运行时之前。**不建议**让 Rust 打包器写 sprite_name（packer 引擎无关、不该知 Unity 命名，越界 + 反 YAGNI）。

### 置信度 + 待验

- 即时病因在 atlas 侧（三空 + folder packable）：**高**。
- 具体是 folder 失效 / Packer 禁用 / Include 未勾 / 没 Pack Preview 中哪一条：**需运行时 `spriteCount` 区分**（0 → 候选 1 三子因之一）。

## B3 — tips 被挤出屏幕外

### 根因（agent + git `d6cfdd9` 双证）

absolute/overlay 是 v1.4-a **蓄意推迟到 v1.4-b** 的设计缺口（spec §7.3 注记「flex 流式非覆盖，absolute 留 v1.4-b」），**不是回归**。driver `e5f9eb9` 建的 layer 骨架（root column + ui_layer + tips_layer）假设 overlay 能用，但核心还没实现。

`_tipsLayer` 是 root column 的第二个流式子项（`LoomShowcaseDriver.cs:83-87`），`_uiLayer` 的 `flex-grow:1` 吃光 1920px，tips_layer（无显式高度、无 flex-grow）被 taffy 压到 ~0 高、堆到 y=1920（root 底边外）。围栏无 `position:absolute`（`apply_decl` 无 `"position"` arm → `:558 _ => false` 静默忽略；`fence_contract.rs:127-137` 锁定），没有「脱离流」语义。

### 围栏内可用「层叠/覆盖」手段

| 手段 | 支持？ | 能否 overlay |
|---|---|---|
| **transform:translate(x,y)** | 支持（mapping.rs:554-556；不进 taffy、不占布局空间） | **能**（唯一干净工具） |
| margin（含负值） | 仅 shorthand 支持，负值未测 | 能（风险略高） |
| paint order（DOM 序） | 隐式支持 | 半（只解 z 序，不解位置叠加） |
| z-index / 层机制 | **无** | 不能 |
| position:absolute | 围栏外静默忽略 | 不能 |

### 修复（推荐 driver 妥协，YAGNI）

只改 `LoomShowcaseDriver.cs:84-85` 两行 CSS：
- `_uiLayer`：`"flex-grow:1"` → `"height:1920px;flex-shrink:0"`
- `_tipsLayer`：追加 `"height:1920px;flex-shrink:0;transform:translate(0px,-1920px)"`

**原理**：两子项都显式 1920 + `flex-shrink:0` → column 内容总 3840，但 root overflow:visible 不裁剪；tips_layer 布局位置 (0,1920,1080,1920)，`transform:translate(0,-1920)` 经 `scene/transform.rs:40-46` 把 world 原点拉到 (0,0) → 视觉完整覆盖 ui_layer；子 toast 由 `justify-content:flex-end;align-items:center` 定到屏幕底中。DOM 序保证 tips_layer 后画 = 最上层（无需 z-index）。正用上 CLAUDE.md 不变量点名的「transform 偏移不占布局空间」。hit 也吃 world_transform（hit.rs:85）→ toast 仍可在视觉位置命中。

**副作用**：toast 数量变化时位置稳定（tips_layer 恒 1920、transform 恒 -1920，与 toast 个数/有无完全解耦）。唯一弱点——「column 溢出 + transform 回拉」不像 `position:absolute` 从 HTML 一眼读出 overlay，但污染只限 driver 内部，不进围栏/核心契约。

**备选（负 margin）**：`_tipsLayer` 用 `margin:-1920px 0 0 0` 让流占位坍缩 → layout_rect 直接 (0,0)，更干净但依赖 taffy 对 flex column 负 margin 的处理（本仓未测）。

### 长期（v1.4-b）

做正经 absolute 定位：`apply_decl` 加 `"position"` + `"top/right/bottom/left"` arm，映射 `taffy_style.position=Absolute` + inset（taffy 0.5 原生支持，父默认 Relative 即包含块）。layout/render/hit **都不用改**（absolute 项照常产 layout_rect、走 world_transform、命中如常）。改动面：style/mapping.rs + fence_contract.rs + fence.md + main-design.md（约 1 天）。**是围栏扩张**，影响 AI 预测契约，需走完整围栏维护流程。等出现第二个 overlay 用例（modal/dropdown/tooltip/drag-ghost）再做。

### 置信度 + 待验

- 根因/机制：**高**。
- transform 方案有效：**高**（transform 路径有单测覆盖 + CLAUDE.md 不变量背书）。
- **待验**：root overflow:visible 默认不裁，tips_layer 布局 y=1920..3840 屏外但不被裁，transform 拉回后视觉正确——理论上成立（`translate_stacks_on_layout_rel` 测试），建议实机 dump tips_layer.layout_rect 确认。

## B4 — 文字随机重叠/上下错位

### 根因（已读 TextRasterizer.cs:55/67 + MirrorPool.cs:173/200 核实）

Unity 动态字体 atlas rebuild 当帧竞态。
- `BuildMesh` 当帧 `RequestCharactersInTexture`（TextRasterizer.cs:55，新字触发 atlas rebuild）→ **同帧**立刻 `GetCharacterInfo`（:67）取**抖动的 box/UV** → 直接进 quad 顶点（:69-72 `PenX+info.minX` 等）和 UV（:80-83 `info.uvBottomLeft` 等）。
- LoomGUI 缺 fgui `Stage.cs:828-836` 的「rebuild 当帧二次渲染」机制——注释 TextRasterizer.cs:12-14 自承「rebuild 时 UV 变」，但只在**下帧**检测 FontVersion 重光栅。

### quad 顶点计算式（位置错位直接原因）

```
pl = PenX + info.minX    // Rust 笔位（确定）+ Unity glyph box（抖动）
pr = PenX + info.maxX
pt = PenY - info.maxY
pb = PenY - info.minY
```
`PenX/PenY` 来自 Rust TextLayout（`text/layout.rs:289-296`，完全确定）；`info.minX/maxX/minY/maxY` 来自 Unity GetCharacterInfo，**rebuild 当帧抖动** → quad 边界全偏。UV 同步抖动 → 采样到 atlas 错区 → 渲成别字像素。

### 「随机」真机理（跨节点同帧污染）

一帧内多个 text 节点（共享全局单一 `_font`，LoomStage.cs:38）各自触发 rebuild：
- 节点[0] BuildMesh：请求新字 X → atlas rebuild(v5→v6) → 节点[0] quad 用 v6 UV 建。
- 节点[1] BuildMesh：请求新字 Y → atlas 再次 rebuild(v6→v7) → 节点[1] 用 v7 建，**但节点[0] mesh 仍钉 v6 UV**，atlas 现是 v7 → 节点[0] 渲错位置/错字。
- 节点[2..N] 类推 → 前 N-1 个节点 mesh 被后续 rebuild 作废 → 本帧多节点同时错位。
- 下一帧 fontDirty（5≠final）→ 全重建稳定 → 好。但下下帧又有新字 → 再错。**随机性 = 哪些字首次出现 + 节点遍历顺序 + 哪帧引入**。动态内容（计数器/滚动/tips）每帧引入新字 → 持续错乱（非偶发闪烁）。

### fgui 对照

fgui DynamicFont（`temp/FairyGUI-unity/.../Text/DynamicFont.cs:112-134`）同样「请求后同帧取」，**也踩这个坑**。fgui 的解法不是改 DynamicFont，而是在 `Stage.cs:828-836` 加全局二次渲染：

```csharp
if (BaseFont.textRebuildFlag) {
    // 字体贴图更改了，重新渲染一遍，防止本帧文字显示错误
    Update(_updateContext);
    BaseFont.textRebuildFlag = false;
}
```

### 修复（照搬 fgui 验证过的解法）

改 `MirrorPool.Sync`：
1. L56 附近加 `int versionAtSyncStart = TextRasterizer.FontVersion;`。
2. 主循环照旧，但收集本帧 text 节点的 `(blob 索引 i, node_id)`。
3. 主循环后、L200 前，加二次 BuildMesh：
   ```csharp
   if (TextRasterizer.FontVersion != versionAtSyncStart) {
       // atlas 本帧 Sync 中途 rebuild → 所有 text 节点用现在已稳定的 atlas 重 BuildMesh。
       // 此时所有字形已 Request 进 atlas，二次 BuildMesh 内 RequestCharactersInTexture 不再触发 rebuild，
       // GetCharacterInfo 返回稳定 box/UV。
       foreach (var (i, id) in textNodesThisFrame) {
           if (!_pool.TryGetValue(id, out var ro) || !ro.IsText) continue;
           blob.ReadText(i, out int fs, out Color col, out var glyphs);
           var seg = TextRasterizer.BuildMesh(font, fs, col, blob.Alpha(i), glyphs);
           UploadMesh(ro, seg); ro.Mesh.RecalculateBounds();
           ro.LastFontVersion = TextRasterizer.FontVersion;
       }
   }
   ```
4. L200 latch 条件改 `if (fontDirty || TextRasterizer.FontVersion != versionAtSyncStart) _lastFontVersion = ...`（避免下一帧冗余全重建）。

### 次要 bug（与 B4 正交，建议同 PR）

MirrorPool.cs:173 `needRebuild = fontDirty || LastFontVersion != FontVersion` **不看内容变化** → SetText 纯缓存字（无新字无 rebuild）时 mesh 不重建、显示旧字（症状是「不更新」非「乱」）。推荐 C# 侧给 RenderObj 加轻量内容签名（`glyph_count + 首 codepoint`）比对，零 FFI 改动。

### 附带三级发现（记录待办，非 B4）

`dirty.rs:63-87` text hash 只捕 `font_size + color + glyph_count + 首字 codepoint + 首字 x/y`，同字数同首字不同文本（"hello"→"helps"）hash 撞 → core 误 emit Unchanged → 文字不更新。这是 dirty hash 字段遗漏病（同坑 56/75/76）在 text 路径的实例，建议后续把全量 codepoint 入 hash。

### 置信度 + 待验

- B4 = atlas rebuild 当帧竞态：**0.9**（代码逐行 + fgui 完全同型坑 + fgui 用「整帧重渲染」明确解之；症状全部对齐）。
- 单节点自 rebuild 是否也错：**0.6**（Unity 文档含糊），但跨节点污染无论哪种都成立，不影响根因。
- B4 是**既有 bug**（v1.4-a 无 text 提交），被新 showcase 动态内容放大暴露。
